# Reference Line Generation

This document is the stable pointer for how FirstMove generated the engine
reference lines shown in the app.

If the implementation script is renamed, replaced, or split later, update this
file in the same change. The goal is that a future session can always start
here and find the current source of truth.

## Current Entry Points

Reference line algorithm:

- `scripts/generate-opening-candidates.cjs`

Full opening course pipeline:

- `scripts/run-opening-course-pipeline.cjs`

The orchestrator wraps the full reference and punish/practical branch flow:

1. generate reference candidates
2. deduplicate reference candidates
3. prepare the reference DB payload
4. import reference rows into Supabase
5. prune stale reference rows for the selected openings
6. generate punish/practical branches from the reference output
7. deduplicate practical branches
8. prepare the branch DB payload
9. delete old practical branches for the selected course openings
10. import practical branches and branch metadata
11. restore catalog popularity order from `opening_index`

Current command for the next two missing popularity-ranked openings:

```powershell
node scripts/run-opening-course-pipeline.cjs --next-missing 2
```

Engine/eval caches:

- `scripts/output/best-known-eval-cache.json`
- `scripts/output/lichess-cloud-eval-cache.json`
- `scripts/output/chess-api-eval-cache.json`
- `scripts/output/stockfish-eval-cache.json`

Supabase tables populated by the pipeline:

- `openings_catalog`
- `opening_lines`
- `opening_position_evals`

`opening_lines.eval_cp_by_ply` is written as a dense White-perspective
centipawn timeline. Index `0` is the starting board, and each later index is
the board evaluation after that SAN ply has been played. Generators keep evals
that were already produced during accepted-line search/checkpointing, then
replay only missing plies before writing output. The practice board uses this
timeline first, with `opening_position_evals` only as a fallback for older or
incomplete rows.

## Popularity Index And Learner Exposure

The popularity-ranked opening backlog is sourced from Lichess Explorer counts
stored in `public.lichess_opening_popularity` and exposed through
`public.opening_index`.

Populate or refresh that index with:

```powershell
node scripts/fetch-lichess-popularity.cjs
```

Use narrower/resumable forms when needed:

```powershell
node scripts/fetch-lichess-popularity.cjs --populate-only
node scripts/fetch-lichess-popularity.cjs --fetch-only
node scripts/fetch-lichess-popularity.cjs --type opening
node scripts/fetch-lichess-popularity.cjs --eco-volume c
```

The learner-facing Openings list should use `opening_index` for popularity
ordering, but generated FirstMove course content remains in `openings_catalog`,
`opening_lines`, and `opening_line_branch_metadata`.

A course is complete for learner exposure only after the full course pipeline
has run:

```powershell
node scripts/run-opening-course-pipeline.cjs --openings "<opening name>"
```

Or run the next N missing openings from the popularity-ranked backlog:

```powershell
node scripts/run-opening-course-pipeline.cjs --next-missing 2
```

The single orchestrator is the user-facing entrypoint. It runs reference
generation before branch generation so reference sync cannot prune newly
generated practical branches.

## Current Algorithm Summary

Reference generation starts from Lichess-authoritative named opening anchors
from `lichess-org/chess-openings`.

After the named anchor, reference continuations are generated by best engine
play for both sides. These are reference continuations, not practical branch
lessons.

Engine authority order:

1. best-known local eval cache
2. cached Lichess cloud eval
3. cached Chess-API eval
4. live cloud engine, if available
5. local Stockfish fallback

The best-known cache keeps one result per normalized FEN and ranks sources:

1. Lichess cloud
2. Chess-API
3. Stockfish

Within the same provider, deeper evals replace shallower evals.

## Reference Stopping Model

Reference lines use one shared tabiya/reference stopping model. Do not make
reference stopping depend on tactical, strategic, setup, or forcing line type.
Those categories are available for future branch generation, not for reference
endpoint behavior.

The stopping model considers:

- eval stability
- top-move gap
- tactical volatility
- unresolved capture decisions
- pending recaptures
- material debt and nearby recovery
- king safety
- development / recognizable tabiya shape

If the current endpoint is not clean and the line reaches a cap, the generator
rolls back to the best mature reference checkpoint it saw earlier.

Use this flag to debug why a line stopped or rolled back:

```powershell
node scripts/generate-opening-candidates.cjs --starts-with "Italian Game: Deutz Gambit" --limit 1 --output scripts/output/tmp-deutz-debug.json --continuation-mode reference-best-play --cloud-eval-mode authoritative --trace-reference-checkpoints
```
